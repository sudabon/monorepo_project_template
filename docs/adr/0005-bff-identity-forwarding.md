# 0005: BFF から API へのユーザ識別と転送検証

- 状態: 採用
- 日付: 2026-09-06

## 判断

転送用のユーザ識別ヘッダは `X-User-ID` とする。BFF は入口で同名ヘッダを削除し、
認証済みセッションから導いた値を outbound で設定する。`Header.Set` だけに頼らず
`Del` してから `Set` する。

リクエスト ID は Phase 2 の `X-Request-ID` をそのまま使う。クライアント値が
あれば引き継ぎ、なければ生成して API へ渡す。

アプリケーション層で「BFF からの転送であること」を検証する共有秘密は、
テンプレート初期値では入れない。backend はインターネットに出さず、
セキュリティグループ等のネットワーク層で到達経路を BFF に限定する。

## 根拠

`X-User-ID` は識別の意味がヘッダ名から分かり、プロキシが付与しがちな
`X-Forwarded-User` と混同しにくい。Go の `net/http` は MIME 正規化するため、
`X-User-Id` / `x-user-id` も同じキーとして削除できる。

共有秘密（例: `X-BFF-Internal-Token`）は、backend が VPC 外や他タスクから
直接届く構成になったときの防御になる。初期値の構成ではネットワーク前提を
崩すコードを API に足さず、その前提が崩れた案件で足す。秘密の配布・回転・
失敗時の 403 をテンプレートに先行して置くと、認証を BFF に閉じる方針と
別に API 側の認証ロジックが増える。

## 案件で API 層の検証を足すべきとき

- backend にパブリック IP や広い SG が付く、または開発者が API ポートを直接叩く
- ゼロトラストでタスク間も相互 TLS / トークンを要求する
- コンプライアンスがアプリ層の送信元検証を求める

その場合はネットワーク制限を残したうえで、BFF だけが知る秘密をヘッダで付与し
API で検証する。クライアント由来の同名ヘッダは BFF と同様に削除してから設定する。
