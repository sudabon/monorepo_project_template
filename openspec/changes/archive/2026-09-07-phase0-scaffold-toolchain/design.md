## Context

新規リポジトリであり、既存コードは存在しない。以降の Phase 1〜6 がすべてこの土台の上に乗るため、ここで決めた入口（`make`）とジョブ分割はあとから変えにくい。

制約は次の 4 点。

- 運用は原則ひとり。同時 5〜8 案件の並行保守を想定するため、案件ごとに CI を読み解く状態にしない
- モノレポビルドツール（Nx / Turborepo）は非目標。pnpm workspace + Makefile で完結させる
- CI が実行するコマンドはすべてローカルから同じ形で実行できること
- テンプレートは初期値であって規約ではない。clone 後に案件側で書き換えられる前提で書く

動機は proposal.md - Why を参照。要求は specs/build-toolchain/spec.md を参照。

## Goals / Non-Goals

**Goals:**

- `make` を唯一のタスク入口とし、CI ワークフローを `make <target>` の呼び出しだけで構成する
- Go / TypeScript / API 契約の 3 系統を独立したワークフローに分け、パスフィルタで無関係なジョブを走らせない
- ツールチェーンのバージョンを単一の値に収束させ、CI とローカルで差が出ない状態にする
- Phase 1 以降が `make gen` などに追記するだけで済む拡張点を用意する

**Non-Goals:**

- ビルドキャッシュ・タスクグラフ最適化（Nx / Turborepo 相当）。並列化は必要になった時点で検討する
- リモートキャッシュ、self-hosted runner
- 本フェーズでのアプリケーションコードの実装（骨格ディレクトリのみ）
- デプロイワークフロー（本テンプレートの範囲外）

## Decisions

### D1: タスクランナーは Makefile

pnpm scripts ではなく `Makefile` をルートの入口にする。Go と TypeScript の両方を同じ語彙で扱う必要があり、pnpm scripts に Go のタスクを寄せると Node がないと Go のテストすら流せなくなる。

- 代替案: `package.json` scripts に統一 → Go 側が Node に依存する。却下
- 代替案: Taskfile / just → 学習コストと追加インストールが増える。`make` は環境に既にある。却下
- 各ワークスペースは自前のタスク定義（`go test`、`pnpm -r`）を持ってよいが、ルート Makefile はそれを呼び出すだけの薄い層に保つ

### D2: `make check` は CI と同じ順序で全部を実行する

`check` を `fmt` チェック → `lint` → `gen` の差分検証 → `test` → `build` の順で直列に呼ぶ。CI 側は各ジョブでこの部分集合を呼ぶだけにする。「CI では落ちるがローカルでは通る」を構造的に作らないことを優先し、直列実行の遅さは受け入れる。

### D3: ワークフローは 3 本、パスフィルタはワークフローの `on.push/pull_request.paths` で行う

`go.yml` / `web.yml` / `contract.yml` に分ける。ジョブ内での動的な差分判定（dorny/paths-filter 等）は使わない。追加アクションへの依存が増え、スキップ判定がログを読まないと分からなくなるため。

- 副作用として、required status check を設定するとスキップされたジョブで PR がブロックされ得る。これは「必須チェックはパスフィルタを持たない集約ジョブに寄せる」ことで回避する方針とし、実装時に集約ジョブの要否を判断する

### D4: バージョンはこの設計では決めず、実装時に最新安定版を採用して記録する

具体的なバージョン番号は設計に固定しない。実装時に調査して完全一致でピンし、採用理由と次のメジャーで壊れそうな点を `docs/STACK.md` に 1 行ずつ残す。`docs/STACK.md` の記載そのものは Phase 6 で本格化するが、Phase 0 で採用したツールチェーンのバージョンはこのフェーズで書き始める。

### D5: 生成物はコミットする（このフェーズでは方針の固定のみ）

`.gitignore` に生成コードを入れない。CI で `make gen && git diff --exit-code` により仕様と生成物のずれを落とす仕組みは Phase 1 で `contract.yml` に実装するが、`.gitignore` の方針はこのフェーズで確定させる。

### D6: E2E ガードの適用範囲

`scripts/check-test-plan.sh` は openspec change に差分がある PR に対し、test-plan.md の存在と `@<change-id>` タグ付きの E2E テストの存在を要求する。ブラウザ操作を伴わない change（本フェーズを含む）では該当するテストが存在し得ないため、ガードに「E2E 観点を持たない change」を許容する経路を用意する。

判定は 2 段階で行う。

**第 1 段階: リポジトリ単位の抑止。** 本リポジトリはテンプレートであり、ここで起票する change は
テンプレート自身を作る作業を表す。テンプレート構築段階では E2E の対象となるアプリケーションが
まだ存在しないため、ガードをリポジトリ単位で無効化する。判定は kit の設定ファイル
`.openspec-e2e-kit.json` の `templateRepo` フラグで行い、真のときだけスキップする。

判定の向きが要点で、フラグが無い・偽・設定ファイル自体が無い場合はガードを有効とする。
テンプレートから作成した案件リポジトリは、Phase 6 のチェックリストでフラグを外すことで
ガードが有効になる。仮に外し忘れても、フラグの削除漏れは全文検索で検出できる（Phase 6 の D2）。
逆向き（案件側で明示的に有効化する）にすると、有効化を忘れた案件でガードが恒久的に死ぬため採らない。

**第 2 段階: change 単位の判定。** ガードが有効なリポジトリでは、test-plan.md の有無で判定する。
E2E 観点を持つ change は test-plan.md を必ず持ち、持たない change は E2E 不要とみなして
タグ付きテストの要求から外す。test-plan.md がある change については従来どおり、タグ付きテストが
存在しなければ失敗させる。E2E 観点があるのに test-plan.md を書き忘れた場合を見逃す点は
トレードオフとして受け入れ、change 起票時のレビューで担保する。

環境変数によるスキップ経路は設けない。ワークフロー側の設定は案件へ引き継がれる際に消し忘れが
起きやすく、ガードが無言で無効になるため。

ガードの実行位置は Go / TypeScript / 契約のいずれの系統にも属さない（`openspec/changes/` の差分が
トリガー）。D3 の 3 本のワークフローには載らないため、タスク 3.5 で要否を判断する集約ジョブに含めるか、
専用ワークフローを追加するかを実装時に決める。どちらでも、パスフィルタで無効化されないことが条件。

## Risks / Trade-offs

- **`make check` の直列実行が遅くなる** → 初期は許容する。体感で問題になった時点で、ローカル向けに並列ターゲットを追加し、`check` の定義（CI と同一順序）は変えない
- **パスフィルタと required status check の組み合わせで PR がブロックされる** → D3 のとおり集約ジョブで回避する。実装時にブランチ保護設定と合わせて確認する
- **Renovate の自動マージが壊れた依存を取り込む** → 自動マージは CI 通過を条件とする。CI の網羅性が担保になるため、Phase 1 以降で検証内容が増えるほど安全側に寄る
- **バージョンを完全一致でピンすることで更新頻度が上がる** → 週次グループ化により PR 本数を抑える。トレードオフとして受け入れる
- **テンプレート由来の識別子（モジュールパス等）が案件側に残る** → Phase 6 の README チェックリストで回収する。本フェーズでは検出可能な形（一意な文字列）にしておく

## Migration Plan

新規リポジトリのため移行対象なし。ロールバックはコミットの revert で足りる。
