## Context

Phase 3 までで BFF が 401 を返し、CSRF トークンをセッション確認の応答から取得できる状態になっている。SPA はこの BFF だけを相手にする。フロントは静的ファイルとして S3 + CloudFront に置き、`/api/*` は BFF のオリジンにルーティングする前提（Phase 3 の D6）。

非目標として、Next.js / Remix / TanStack Start などの SSR・メタフレームワークは採用しない。Redux などの大掛かりな状態管理も入れない。UI ライブラリは依存にしない（コピー型）。

動機は proposal.md - Why を参照。要求は specs/web-app-shell/spec.md を参照。

## Goals / Non-Goals

**Goals:**

- ビルド成果物を全環境で 1 つにし、環境差分を配信時の設定ファイルだけに閉じる
- 認証・エラー・フォームの扱いを骨格側で決め、画面を増やしても同じ手当てを繰り返さない
- 依存を増やさずに、案件側で自由に書き換えられる UI 部品を持つ

**Non-Goals:**

- SSR / SSG、メタフレームワーク
- ダークモード（案件で必要になったら足す）
- 国際化（i18n）
- デザインシステムとしての UI ライブラリ化・npm 公開
- 監視サービスへの実接続（差し込み口のみ）

## Decisions

### D1: 環境設定は起動時に `/config.json` を fetch する

Vite の `import.meta.env` によるビルド時埋め込みは使わない。環境ごとにビルドし直す運用は、案件が増えるほど「どの成果物がどの環境か」を追えなくなる。

- 取得は起動処理の最初に 1 回だけ行い、React のレンダリング開始前に解決する。取得前のコンポーネントが未設定のクライアントを掴む状態を作らない
- 取得した内容は zod で検証する。不正な値のまま通信を試みない（specs の該当シナリオ）
- 失敗時のフォールバックは「既定値で動かす」ではなく「設定を読めなかったことを表示する」。誤った接続先で動くより、動かない方が安全
- `config.json` は CloudFront で `no-cache` にする必要がある。配信設定の要件として `docs/` に記載する（記載の本格化は Phase 6）

### D2: `noUncheckedIndexedAccess` を有効にする

配列・インデックスアクセスの結果が `undefined` になり得ることを型で強制する。導入コストは上がるが、後から有効化すると既存コード全体が赤くなるため最初から入れる。

### D3: 認証状態は BFF のセッション確認エンドポイントを唯一の情報源にする

SPA 側にログイン状態のフラグを持たない。ルータの `beforeLoad` でセッション確認の結果を待ち、未認証ならログインへ遷移させる。表示してから消す（フラッシュ）を避けるため、判定は遷移完了前に行う。

- セッション確認の結果は TanStack Query のキャッシュに載せ、`beforeLoad` からはキャッシュ経由で読む。画面ごとに毎回問い合わせない
- CSRF トークンもこの応答から取得する（Phase 3 の D2）

### D4: QueryClient の既定値は明示的に決め、理由をコメントに残す

`staleTime` / `retry` / `refetchOnWindowFocus` を既定のままにしない。既定値は「なんとなくそうなっている」状態を作り、案件ごとに挙動が違う原因になる。値そのものより「なぜその値か」をコメントで残すことを重視する。

- `retry` は認証エラーとクライアントエラーに対しては行わない。再試行しても結果が変わらないため
- 値の初期設定は案件側で変える前提。テンプレートは初期値であって規約ではない

### D5: グローバル `onError` はエラーの分類だけを行い、表示は各層に任せる

401 → ログインへ、5xx → トースト、それ以外 → 表示に回す。分類のロジックを 1 か所に置き、各画面で `catch` を書かせない。「それ以外」を握りつぶす実装にしないことが要点。

### D6: ローディングは Suspense を使わない

TanStack Query の `isPending` を使い、ローディング表示を各画面のコンポーネント内で行う。Suspense と ErrorBoundary の組み合わせは、境界の設計を誤ると原因の切り分けが難しくなる。テンプレートとしては経路が読みやすい方を選ぶ。

- 代替案: Suspense に統一 → ローディングの記述量は減るが、`beforeLoad` での認証判定と描画中断が絡んで挙動を追いにくい。却下
- 統一することが目的なので、案件側で Suspense に寄せるのは自由。混在させないことだけを規約とする

### D7: サーバ検証エラーのマッピングは契約のフィールド識別子を鍵にする

Phase 1 の D4 で決めたフィールド識別子を、react-hook-form のフィールド名に変換する共通関数を 1 つ置く。変換できなかったエラーはフォーム全体のエラーとして表示する。捨てない。

### D8: UI 部品はコピー型で持つ

shadcn/ui の方式に倣い、生成されたコードを自分のソースとして持つ。パッケージ依存にしない。メジャーアップグレードのたびに全画面が壊れるリスクを、初期の記述量と引き換えに避ける。

## Risks / Trade-offs

- **起動時の設定 fetch が初期表示を遅らせる** → 1 リクエスト分の遅延は受け入れる。`config.json` は小さく、CloudFront から配信されるため実害は小さい
- **`config.json` のキャッシュ設定を誤ると設定が反映されない** → 配信要件として `docs/` に明記する。Phase 6 の CloudFront 設定記載と整合させる
- **`noUncheckedIndexedAccess` による記述量の増加** → 案件側で無効化できる。最初から有効にしておく方が後から入れるより安い
- **Suspense を使わない選択が将来の React の方向性と合わない** → 統一されていれば移行は機械的に行える。混在させないことを規約にすることで移行コストを抑える
- **UI 部品の内製により、アクセシビリティの実装が自前になる** → キーボード操作とフォーカス管理を持つ部品（モーダル・トースト）は特に注意が必要。実装時に確認項目を明示し、不足は `// TODO(template):` で残す
- **BFF のセッション確認に依存するため、BFF 未起動では何も表示できない** → その場合も白画面にせずエラー表示に落とす（specs の該当シナリオ）

## Open Questions

- 「API 停止時に白画面にならない」を E2E で押さえるべきか。テンプレート方針では Playwright のスモークを Phase 5 の 1 本のみとしているため、本フェーズでは Testing Library に委譲している。この制約を緩めるかは判断が必要だが、緩めた場合の追加は本 change に test-plan.md を追加して実装タスクを足す形になり、既存の specs・設計方針・タスク構成は変わらない
