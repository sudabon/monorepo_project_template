# Test Plan

このアーティファクトは specs/ 配下の各 Requirement のシナリオ(受け入れ基準)を
E2E で検証可能な観点に翻訳したものである。受け入れ基準の原本は specs のシナリオで
あり、本ファイルで新しい仕様を定義してはならない。

## 本 change における E2E の方針

テンプレートの方針により Playwright のスモークは 1 本のみとする(指示書 Phase 5)。
そのため下表の E2E 観点はすべて、単一のスモークテストの中で `test.step` に分けて
検証する。テストには `@phase5-fullstack-vertical-slice` と、下表のすべての
`@TP-NNN` タグを付与する。

これは e2e-conventions の「1 テスト = 1 検証意図」と緊張関係にある。本 change では
スモークの検証意図を「参照実装が端から端まで壊れていないこと」と定義して 1 本に収める。
テスト本数の方針を変える判断が出た場合は、本ファイルの観点分割から見直す(報告事項)。

## E2E観点一覧

| TP-ID | 対応シナリオ | 前提(fixture) | 操作の意図 | 期待結果 | リスク |
|-------|-------------|---------------|-----------|---------|--------|
| TP-001 | 作成と編集 / 作成した内容が一覧に現れる | `authenticated-user` | 認証済み利用者が一覧から作成フォームへ進み、有効な内容を送信する | 作成が成功し、一覧に当該項目が現れる | 高 |
| TP-002 | 一覧から詳細への遷移 / 詳細の表示 | `authenticated-user` + TP-001 で作成した項目 | 一覧の項目から詳細画面へ進む | 選んだ項目の内容が詳細画面に表示される | 高 |
| TP-003 | 作成と編集 / 編集した内容が詳細に反映される | `authenticated-user` + TP-001 で作成した項目 | 詳細から編集フォームへ進み内容を更新する | 更新が成功し、詳細画面に更新後の内容が表示される | 高 |
| TP-004 | 確認を伴う削除 / 確認を取り消す | `authenticated-user` + TP-001 で作成した項目 | 削除を実行したうえで確認を取り消す | 削除されず、一覧に残る | 中 |
| TP-005 | 確認を伴う削除 / 確認して削除する | `authenticated-user` + TP-001 で作成した項目 | 削除を実行し確認を承認する | 対象が削除され、一覧から消える | 高 |
| TP-006 | 一覧画面の検索条件とページ位置の URL 保持 / 検索条件がリロード後も保持される | `sample-resources-multi-page` | 検索条件を変更してからリロードする | 変更後の検索条件が維持された一覧が表示される | 高 |
| TP-007 | 一覧画面の検索条件とページ位置の URL 保持 / ページ位置がリロード後も保持される | `sample-resources-multi-page` | 2 ページ目へ移動してからリロードする | 2 ページ目の内容が表示される | 中 |

## E2E対象外(委譲先と理由)

| シナリオ | 委譲先 | 理由 |
|---------|--------|------|
| 一覧画面の検索条件とページ位置の URL 保持 / URL の共有 | ユニットテスト(search params スキーマの解釈)＋ TP-006 | 別セッションで同一 URL を開く操作は TP-006 のリロードと検証内容が重複する。URL 単体から状態が復元できることは TP-006 で担保される |
| 一覧から詳細への遷移 / 該当データがない一覧(空データ) | Testing Library(空応答をモック) | 空データ状態を E2E で作るにはシードの出し分けが必要で、スモーク 1 本の構成に収まらない。表示分岐はコンポーネント単位で確実に検証できる |
| 作成と編集 / サーバ検証エラーの表示(異常系) | Testing Library(検証エラー応答をモック)＋ Phase 2 の Go 統合テスト | サーバ側で拒否される入力を安定して作るには API 側の状態操作が必要。応答形式は Phase 2、画面への反映は Phase 4 のマッピング共通処理でそれぞれ検証済み |
| 権限境界(未認証で保護ルートを開く) | Testing Library(ルータのテスト)＋ Phase 3 の Go 統合テスト(401) | Phase 4 の認証ガードと Phase 3 の 401 応答で二重に担保されている。スモークはログイン済みの導線に集中させる |
| 多重送信(作成・削除の連打) | Testing Library(送信中の再送抑止)＋ Phase 2 の Go 統合テスト | 連打のタイミング再現は E2E ではフレークの原因になりやすい。抑止はコンポーネント単位で決定的に検証できる |
| ネットワーク断・API 停止時の表示 | Phase 4 の Testing Library(全リクエスト失敗をモック) | Phase 4 の `web-app-shell` で定義済みの振る舞いであり、本 change の要求ではない |

## タグ対応

- すべての実装テストに `@phase5-fullstack-vertical-slice` と `@TP-001`〜`@TP-007` を付与すること
- 単一のスモークテストに全 TP タグを付ける構成とし、`test.step` で観点ごとに区切ること
