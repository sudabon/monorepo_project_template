## Context

Phase 0〜5 で実装が揃い、各フェーズで下した判断は design.md と一部の ADR に散っている。本フェーズはそれを、新規案件の立ち上げと日々の運用という 2 つの用途に向けて再構成する。

利用者は 2 種類いる。1 つは新規案件を立ち上げる人（＝自分）、もう 1 つは Coding Agent。前者には手順とチェックリストが要り、後者には階層ごとに絞られた文脈が要る。この 2 つを 1 つのファイルに混ぜない。

動機は proposal.md - Why を参照。要求は specs/template-bootstrap/spec.md を参照。

## Goals / Non-Goals

**Goals:**

- README を読むだけで新規案件を立ち上げられる状態にする
- 運用で判断が要る場面（依存更新、脆弱性警告、DB アップグレード、障害初動）に対して、都度考えずに済む基準を置く
- 各フェーズの判断を ADR に集約し、次の案件で同じ検討をやり直さない
- Coding Agent が必要な文脈だけを読む構造にする

**Non-Goals:**

- インフラのコード（Terraform）そのもの。配信要件は記載するが、実装はテンプレートの範囲外
- 全案件で後から一括更新できる仕組み。テンプレートは初期値であって規約ではない
- ドキュメント生成の自動化。手で書いて手で直す
- 監視・アラートの設定内容。差し込み口の説明に留める

## Decisions

### D1: README は「立ち上げ手順」に特化し、設計の説明を書かない

README の読者は、今から案件を始める人。設計の背景は `docs/` と ADR に置き、README からはリンクする。README が長いほど読まれなくなるため、チェックリストと最初のコマンドを先頭に置く。

### D2: 書き換えチェックリストは、検証可能な形にする

「モジュールパスを変更する」だけでは適用漏れが分からない。テンプレート固有の識別子を 1 つに揃えておき、チェックリスト適用後にその文字列を全文検索して残っていないことを確認する手順を含める。

- 識別子を分散させない設計は Phase 0 の時点で意識している。ここでその前提を使う
- ドキュメント内の言及（このチェックリスト自身など）は検索から除外する必要がある。除外の指定も手順に含める

### D3: 依存更新のレビュー基準は「本番配信物に入るか」で二分する

`npm audit` の警告は数が多く、すべてを同じ優先度で扱うと運用が破綻する。devDependencies の脆弱性は本番配信物に届かないため、対応の緊急度を分ける。判断の軸を 1 つに絞ることで、警告を見た瞬間に扱いが決まる状態にする。

- ビルド時に実行されるツールのサプライチェーン攻撃という別軸のリスクは残る。この軸も明記し、「本番に入らない＝無視してよい」と読まれないようにする

### D4: ADR は判断ごとに 1 ファイル、フェーズ順に採番する

各フェーズの design.md に書かれた Decisions のうち、後から覆すコストが高いものを ADR に昇格させる。design.md は change のライフサイクルで archive されるため、長期に参照される判断は ADR 側に置く。

- 対象の目安: 契約を手書きにする判断、認証を BFF に閉じる判断、環境設定を実行時 fetch にする判断、UI をコピー型にする判断、層構造と依存方向の判断
- 各フェーズで既に ADR にした項目は重複させず、参照に留める

### D5: AGENTS.md は 4 つ、ルートは案内に徹する

ルート / `apps/api` / `apps/bff` / `apps/web` の 4 つ。ルートには共通ルール（コミット規約、`make` を使うこと、生成物を編集しないこと）と、作業対象に応じてどれを読むかの案内だけを書く。フロントの作業で Go の文脈を読ませないことが分割の目的。

### D6: 配信要件は「なぜそうするか」とセットで書く

`index.html` を no-cache にする理由（デプロイ後に古い HTML が古いアセットを指す）、ハッシュ付きアセットを immutable にする理由、403/404 を `/index.html` に 200 で返す理由（SPA のルーティング）を添える。理由がないと、案件側で設定を変えたときに何が壊れるか分からない。

- `config.json` も no-cache が必要（Phase 4 の D1）。アセットと同じ扱いにしないよう明記する

## Risks / Trade-offs

- **ドキュメントが実装から乖離する** → 乖離を完全には防げない。乖離しやすい箇所（バージョン一覧）は生成元を明示し、確認手順を RUNBOOK に置く
- **ADR が「書いたきり」になる** → 覆された判断は ADR を削除せず、後続の ADR で上書きする運用を明記する
- **README のチェックリストが漏れる** → D2 の全文検索による検証で機械的に検出する。手順の目視確認に依存しない
- **AGENTS.md の分割によりルールが重複・矛盾する** → ルートは案内に徹し、具体ルールは階層側にだけ書く。重複を見つけたら階層側を正とする
- **配信要件を書いても案件側で守られない** → 守られなかった場合に何が起きるかを併記する。禁止ではなく因果で書く
