## Decisions

### D1: 非同期処理を捨てる箇所では拒否も捨てる

**決定**: `ItemDetailPage` の `void confirmDelete();` を、拒否を明示的に受け取る形に変える。エラー通知は現状どおり `MutationCache` の `onError` が担い、ここでは何も表示しない。

**理由**: 失敗時の表示は既に正しく、足りないのは「拒否が誰にも受け取られていない」ことだけ。表示側に処理を足すと通知が 2 回になる。

**代替案**: (a) `mutateAsync` を `mutate` に変える → コールバックで後続処理を書くことになり、`await` の直線的な流れが崩れる。(b) 最上位で `window.onunhandledrejection` を握る → 本当のバグまで隠れる。採らない。

**同種の箇所**: `void` で非同期を捨てている箇所は他に 5 か所あるが、いずれも拒否しない経路（`router.navigate` と `bootstrap` 内で catch 済み）であることを確認済み。今回変えるのは 1 か所に限る。

### D2: ボタンの見た目は関数として公開する

**決定**: `components/ui/button.tsx` から、見た目のクラスを返す関数（`buttonClasses`）を export する。`Button` 自身もそれを使う。リンクは `<Link className={buttonClasses()}>` として同じ定義を参照する。

**理由**: shadcn/ui 方式でコピーして所有する部品は、React コンポーネントの形でしか再利用できないと、`<a>` や `<Link>` に適用したい場面でクラス文字列のコピーが起きる。現に起きており、**コピーされたのは基本クラスだけで `focus-visible:` と `disabled:` が落ちている**。関数として出せば漏れが構造的に起きない。

**代替案**: (a) `Button` に `as` プロパティを足して多態にする → TanStack Router の `Link` は型付きの `to` / `params` を持ち、多態にすると型が壊れやすい。(b) `<Button onClick={navigate}>` に置き換える → 右クリックで開く・新しいタブで開くができなくなる。リンクはリンクのままにする。

### D3: 複数行入力は新しい部品として足す

**決定**: `components/ui/textarea.tsx` を追加する。`Input` と同じ構造（`label` と `invalid` を受け取り、`useId` で `label` と結ぶ）にする。`ItemForm` の `description` をこれに置き換える。

**理由**: 契約が `maxLength: 2000` を与える項目を 1 行の `<input>` で出すのは、参照実装として誤った対応付けを示している。汎用部品は「ボタン・入力・モーダル・テーブル・トースト」と定義されているが、これは最低限であり、契約が要求する形に足すのは方針の範囲内。

### D4: エラーの関連付けは部品側に経路を通す

**決定**: `Input` と `Textarea` に、エラー要素の id を受け取って `aria-describedby` に載せる経路を作る。エラー文の `<p>` に id を与えるのは呼び出し側（`ItemForm`）とする。

**理由**: 現在 `ItemForm` は `<p role="alert">` を入力欄の隣に置いているだけで、両者は関連付いていない。`aria-invalid` は既にあるので、残りは説明の紐付けだけ。部品側に `error` 文字列そのものを渡す設計もありうるが、エラー表示の見た目とレイアウトは画面ごとに変えたいので、id を渡す形に留める。

## Risks / Trade-offs

- **`buttonClasses` の導入で、部品とクラスの二重の入口ができる** → `Button` 自身を `buttonClasses` の利用者にすることで定義は 1 つに保つ。`apps/web/AGENTS.md` に「見た目の再利用は `buttonClasses`。クラス文字列を写さない」と明記する
- **未処理の拒否を握ると本当のバグが隠れる** → 握るのは `confirmDelete` の呼び出し 1 か所に限り、エラーは `onError` を通って利用者に届く経路を維持する。テストで「通知が 1 回」と「拒否が 0 件」の両方を確認する
- **部品が増えるとコピー元としての読む量が増える** → 追加は複数行入力 1 つに留める
- **単体テストでの検証は実ブラウザでの表示を保証しない** → フォーカスリングの有無は jsdom では色として検証できない。そのため「同じ定義を参照していること」を検証対象とし、見た目そのものは検証しない
