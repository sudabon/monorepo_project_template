## MODIFIED Requirements

### Requirement: フォーム検証とサーバ検証エラーの反映

フォームは送信前にクライアント側で入力を検証しなければならない (MUST)。検証規則は、可能な範囲で API 契約の制約に対応していなければならない (MUST)。サーバから契約のバリデーションエラー形式で返された内容は、対応するフォーム項目のエラーとして表示しなければならない (MUST)。対応する項目が特定できないサーバ検証エラーも、利用者に見える形で表示しなければならない (MUST)。項目に表示するエラーは、その項目と支援技術から対応付けられなければならない (MUST)。

#### Scenario: クライアント側の検証で送信が止まる

- **WHEN** 契約の制約に違反する入力でフォームを送信しようとする
- **THEN** 送信されず、該当項目にエラーが表示される

#### Scenario: サーバ検証エラーが項目に反映される

- **WHEN** クライアント側の検証を通過した入力に対し、サーバが特定フィールドのバリデーションエラーを返す
- **THEN** 該当するフォーム項目にそのエラーが表示される

#### Scenario: 項目に対応しないサーバ検証エラー

- **WHEN** サーバが、フォーム上の項目に対応付けられないバリデーションエラーを返す
- **THEN** そのエラーがフォーム全体のエラーとして表示され、無視されない

#### Scenario: エラーと項目の対応付け

- **WHEN** ある項目にエラーが表示されている状態で、その入力欄のアクセシブルな説明を取得する
- **THEN** 表示されているエラー文が、その入力欄の説明として得られる

### Requirement: UI 部品の内製

汎用 UI 部品（ボタン、入力、モーダル、テーブル、トースト）はリポジトリ内のコードとして保持しなければならない (MUST)。UI コンポーネントライブラリを依存パッケージとして追加してはならない (MUST NOT)。部品の見た目を別の要素で再利用する場合は、部品と同じ定義を共有しなければならない (MUST)。スタイル指定を複製してはならない (MUST NOT)。

#### Scenario: UI ライブラリへの依存がない

- **WHEN** `apps/web` の依存宣言を確認する
- **THEN** UI コンポーネントライブラリが依存に含まれていない

#### Scenario: 汎用部品がリポジトリ内に存在する

- **WHEN** 汎用 UI 部品の実体を探す
- **THEN** ボタン・入力・モーダル・テーブル・トーストがリポジトリ内のソースとして存在し、編集可能である

#### Scenario: ボタンの見た目を別の要素で再利用する

- **WHEN** ボタン以外の要素（画面遷移のリンクなど）をボタンと同じ見た目で表示する
- **THEN** ボタン部品と同じ定義から見た目を得ており、キーボード操作時のフォーカス表現と無効時の表現もボタンと一致する
