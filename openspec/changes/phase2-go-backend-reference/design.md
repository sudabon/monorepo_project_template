## Context

Phase 1 で `api/openapi.yaml` から Echo のサーバインタフェースと型が生成されている。本フェーズはそれを実装する側の構造を決める。参考リポジトリ `github.com/sudabon/monorepo_go_project_template` の層の切り方を原則踏襲するが、TypeScript ワークスペースが同居する前提で配置は見直す。

運用前提として、サービスは ECS のタスクとして動き、ALB のターゲットグループからヘルスチェックを受ける。この前提がヘルスチェックの粒度分離と graceful shutdown の要求を生んでいる。

動機は proposal.md - Why を参照。要求は specs/sample-resource-api/spec.md と specs/service-runtime/spec.md を参照。

## Goals / Non-Goals

**Goals:**

- 案件側がコピーして肉付けできる、1 リソース分の完結した参照実装を作る
- 層の境界と依存の向きを、レビューではなく機械的な検査で保証する
- 運用に必要な要素（ヘルスチェック・shutdown・追跡可能なログ）を骨格の側に置き、ハンドラを増やしても手当てが要らない状態にする

**Non-Goals:**

- 認証・認可（Phase 3 の BFF が担う。API は BFF から渡されたユーザ情報を信頼する）
- キャッシュ、非同期ジョブ、イベント配信
- 監視サービスへの実際の接続（フックの空実装のみ。接続は案件側）
- 複数リソース間のトランザクション設計。1 リソースで型を示すに留める

## Decisions

### D1: 層は handler / usecase / domain / repository の 4 層

参考リポジトリを踏襲する。domain にビジネスルールと型を置き、repository のインタフェースも domain 側に置く。実装は外側。handler は生成された Echo インタフェースを実装し、生成型と domain 型の変換を担う。

- 生成型を domain までそのまま持ち込まない。契約が変わるたびに domain が揺れるのを避けるため
- 変換コードの記述量は増える。1 リソースなら許容範囲であり、境界を守る対価として受け入れる

### D2: 依存方向の検査は lint で行い、テストにはしない

依存方向はビルド時に静的に判定できる性質のもので、テストで書くと検査対象の列挙が漏れる。import 制約を宣言的に書ける lint（go-arch-lint 等）を採用し、`make lint` に含める。

- 代替案: `go list` を使った自作スクリプト → 依存が減る利点はあるが、設定の表現力が乏しく違反箇所の出力が弱い。ツール導入時に比較して ADR に残す
- 代替案: テストで検査 → 検査漏れが起きる。却下

### D3: 契約の実装漏れはコンパイルエラーにする

生成された `ServerInterface` を実装する構造体を、インタフェース型の変数に代入する形で束縛する。操作を実装し忘れるとビルドが落ちる。実行時まで気付かない状態を作らない。

### D4: ヘルスチェックは shallow と deep を別パスにする

ALB のターゲットグループには shallow を設定する前提。deep で DB の生死を見ると、DB の一時的な不調でタスクが次々入れ替わり、復旧を妨げる。deep は監視・障害調査用に別途置き、どの依存先が落ちているかを応答に含める。

- deep は依存先ごとの判定結果を返す。「落ちている」だけでは初動が取れないため

### D5: graceful shutdown は待機上限つき

SIGTERM 受信 → 新規受付を止める → 処理中の完了を待つ → 上限到達で強制終了、の順にする。上限は ECS の `stopTimeout` より短く設定しないと SIGKILL に間に合わないため、設定値の意味を `docs/RUNBOOK.md` に書く（記載は Phase 6 で本格化するが、値の根拠はこのフェーズで決める）。

### D6: リクエスト ID はミドルウェアで注入し、`context` で運ぶ

ヘッダから受け取り、なければ生成する。`slog` のハンドラを `context` からリクエスト ID を読むように構成し、各層でロガーを引き回さずに済むようにする。Phase 3 の BFF が ID を付けて転送するため、ヘッダ名は BFF と揃える必要がある。ヘッダ名の決定はこのフェーズで行い、Phase 3 はそれに従う。

実装でのヘッダ名は **`X-Request-ID`**。受信値を context に格納して応答ヘッダにも返し、
未指定なら UUID を生成する。各層は `slog.InfoContext` / `ErrorContext` 等を使う。
Phase 3 の BFF は同じヘッダを API に転送する。エラー本文の契約は変更しない。
業務 API の prefix は `/api`、ヘルスチェックは `/health/shallow` と `/health/deep`。
`SHUTDOWN_TIMEOUT` の既定値は `20s`、ECS の `stopTimeout` より短く設定する。

### D7: マイグレーションツールは選定して組み込む

Go のマイグレーションツールを 1 つ選び、`make` のターゲットから実行できるようにする。選定基準は「バイナリ 1 つで動く」「SQL をそのまま書ける」「ロールバックが書ける」。ORM は採用しない（依存を増やさない原則、および生成された型との二重管理を避けるため）。選定理由は ADR に残す。

### D8: DB を要するテストの実行方法

ユニットテストは DB を要しない層（domain / usecase）に閉じ、repository 層は実 DB に対する統合テストで検証する。統合テストの DB 起動手段（testcontainers か CI サービスコンテナか）を選定し、ローカルと CI で同じ `make` ターゲットから実行できるようにする。

### D9: NUL（U+0000）は 422 のフィールドエラーで拒否する

PostgreSQL text は NUL を保存できず、従来の文字数検証だけでは作成・更新時に 500 となる。
2026-09-06 のユーザ承認に基づき、Item / ItemInput の name / description に NUL 禁止の
pattern と説明を追加する。domain で永続化前に検証し、既存の `validation_error` 形式で
該当フィールドをすべて 1 回の 422 応答に含める。拒否時は作成も更新も行わない。
JSON の `\u0000` はデコード後に NUL となるため拒否するが、文字としてのバックスラッシュ
を含む `\\u0000` や通常の改行は許可する。エンドポイントと応答の型は維持する。

## Risks / Trade-offs

- **層分割によるボイラープレートの増加** → 1 リソースでは冗長に見えるが、案件で 10 リソースに増えたときの読みやすさを優先する。テンプレートは初期値であり、案件側で潰すのは自由
- **依存方向 lint の導入コストとメンテ** → 設定が壊れて検査が空振りする事故が起きうる。違反を意図的に入れて検査が落ちることを確認するタスクを入れる（D2 のシナリオ）
- **deep check を ALB に誤設定すると障害が広がる** → 設定意図をコードコメントと RUNBOOK の両方に書く。パス名で用途が分かる命名にする
- **shutdown 待機上限と ECS の stopTimeout の不整合** → 値の根拠を書き残し、案件側で環境変数から変えられるようにする
- **リクエスト ID のヘッダ名を後から変えると BFF と API の両方に手が入る** → このフェーズで決め、Phase 3 の design から参照する
- **統合テストが CI を遅くする** → パスフィルタで Go 変更時のみ走る構成は Phase 0 で済んでいる。それ以上の最適化は必要になってから
