## Context

Phase 2 で backend API が動いており、リクエスト ID のヘッダ名も決まっている。BFF はその前段に立ち、ブラウザとの境界を担う。SPA は Phase 4 で作るため、この時点では curl で検証できる範囲までを作る。

前提として、フロントは静的ファイルとして S3 + CloudFront に置く。したがって BFF と SPA は別オリジンになる可能性があり、Cookie の属性と CORS の扱いはその前提で決める必要がある。

動機は proposal.md - Why を参照。要求は specs/session-auth/spec.md を参照。

## Goals / Non-Goals

**Goals:**

- 認証を BFF に閉じ込め、ブラウザには httpOnly Cookie しか渡さない
- Cookie セッション前提で必須になる CSRF 保護を、更新系エンドポイントに漏れなく適用する
- backend が「認証済みユーザは誰か」を BFF から受け取れる形にし、backend 側に認証ロジックを持ち込まない

**Non-Goals:**

- 認可（ロール・権限）の設計。テンプレートでは認証までに留め、案件側で足す
- 外部 IdP との連携（OIDC / SAML）。差し込み口の形だけ意識し、実装はしない
- 多要素認証、パスワードリセット、アカウント登録フロー
- BFF でのレスポンス集約・整形。本フェーズでは転送に留める

## Decisions

### D1: セッションはサーバ側で状態を持つ

セッション識別子だけを Cookie に入れ、実体はサーバ側に持つ。JWT をそのまま Cookie に入れる方式は採らない。ログアウトで即座に失効させられること（specs の失効要求）が理由。

- 保存先はプロセス内メモリでは要件を満たさない（ECS で複数タスクが動く、デプロイで消える）。外部ストアを選定する
- 選定は「依存を増やさない」原則と衝突する。backend が既に使う DB を流用するか、専用のストアを入れるかを比較し、ADR に残す

### D2: CSRF 対策は double submit ではなく、セッション紐付けのトークンにする

セッションに紐付いた CSRF トークンをサーバ側で保持し、リクエストのヘッダと突き合わせる。SameSite=Lax は主要な導線を塞ぐが、それだけを防御にしない。

- SPA はトークンをセッション確認のエンドポイントの応答から取得する（専用エンドポイントを増やさない）
- CSRF トークンは httpOnly にしない。JavaScript から読めなければヘッダに載せられないため。セッション本体が httpOnly であることとは目的が異なる
- 適用対象は「状態を変更するリクエスト」とし、ミドルウェアでメソッドを基準に一律に掛ける。エンドポイントごとの opt-in にすると漏れる

### D3: 未認証は 401、リダイレクトしない

SPA が遷移を制御するため、BFF はステータスコードだけを返す。302 を返すと fetch が透過的に追随し、SPA 側で「ログイン画面の HTML が JSON として返ってきた」状態になる。

### D4: ユーザ情報の転送はヘッダで行い、クライアント由来の同名ヘッダは必ず破棄する

転送用のヘッダ名を決め、BFF の入口で同名ヘッダを無条件に削除してからセッション由来の値を設定する。「上書きするから大丈夫」ではなく「削除してから設定する」順序にする。複数値ヘッダの場合に前の値が残るため。

- backend は BFF 以外から直接叩かれない前提だが、その前提はネットワーク層（セキュリティグループ）で担保する。アプリケーション層でも BFF からの転送であることを検証する手段の要否を、実装時に判断して ADR に残す

### D5: リクエスト ID は Phase 2 で決めたヘッダ名に従う

BFF が入口で受け取り（なければ生成し）、backend への転送時に同じヘッダ名で付ける。BFF 自身のログにも同じ ID を出す。これで SPA → BFF → backend の 1 本のリクエストが同じ ID で追える。

### D6: Cookie 属性と CORS の前提

`SameSite=Lax` を初期値とする。SPA と BFF が別オリジンになる場合、Lax では Cookie が送られないケースが出るため、配信構成の前提を明示する必要がある。

- 初期値の前提: CloudFront で SPA と BFF を同一オリジンに揃える（`/api/*` を BFF のオリジンにルーティングする）。この前提を `docs/` に記載し、案件側で構成が異なる場合に何を変えるかを書く
- この前提を採らない場合は `SameSite=None; Secure` と CORS の credentials 設定が必要になり、CSRF の防御が実質トークンのみに依存する。その差分を明記する

## Risks / Trade-offs

- **セッションストアの選定が依存を増やす** → backend の DB 流用と専用ストアを比較し、案件の規模で選べるよう ADR に判断基準を残す。テンプレートは初期値であって規約ではない
- **CSRF トークンをセッション確認の応答に載せることで、応答の役割が 2 つになる** → エンドポイントを増やさない利点を優先する。トークンのローテーション方針を実装時に決める
- **SameSite=Lax の前提が案件の配信構成と食い違う** → D6 のとおり前提を文書化する。食い違いに気付かず本番で Cookie が送られない事故が最も痛いため、`docs/` の記載を Phase 6 待ちにせず本フェーズで書く
- **クライアント由来ヘッダの破棄漏れによる成りすまし** → 削除してから設定する順序を守り、詐称シナリオをテストで固定する（specs の該当シナリオ）
- **backend が BFF 以外から叩かれる構成になった場合の無防備さ** → D4 の判断を ADR に残し、案件側が気付ける状態にする

## Open Questions

- セッションの有効期限とスライディング更新の方針。値の選択は仕様・タスク構成を変えないため、実装時に初期値を決めて `docs/` に根拠を書く
