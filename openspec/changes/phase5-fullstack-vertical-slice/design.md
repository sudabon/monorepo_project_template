## Context

Phase 2〜4 の成果物が揃っている。本フェーズは新しい仕組みを足すのではなく、既存の部品を組んで 1 リソースを貫通させる。E2E を動かすには API・BFF・SPA の 3 プロセスと DB が同時に必要になり、その起動をどう扱うかが本フェーズ固有の設計課題。

E2E の実装規約は `docs/E2E_CONVENTIONS.md` に従う（ロケーターの優先順位、Page Object、fixture、タグ付け）。

動機は proposal.md - Why を参照。要求は specs/sample-resource-ui/spec.md を参照。

## Goals / Non-Goals

**Goals:**

- 1 リソースを DB からブラウザまで通し、案件がコピーできる完結した参照実装にする
- 一覧の状態を URL に持たせ、リロードと共有に耐える形を初期値にする
- 貫通の回帰を検出するスモークを 1 本だけ置き、CI で回す

**Non-Goals:**

- 複数リソース、リソース間の関連
- 一括操作、CSV 入出力、並び替えの網羅
- 楽観的更新（optimistic update）。テンプレートでは素直な再取得に留める
- 画面デザインの作り込み。骨格と動作の確認が目的

## Decisions

### D1: 一覧の状態は URL を唯一の情報源にする

検索条件とページ位置をコンポーネントの state に持たない。TanStack Router の型付き search params をそのまま読み、変更時は URL を書き換える。state と URL の二重管理をしないことで、リロード・戻る・共有がすべて同じ経路で成立する。

- 型付き search params のスキーマは zod で定義し、不正な URL パラメータは既定値にフォールバックする
- 代替案: state を持ち URL に同期する → 同期漏れが起きる。却下

### D2: 更新後は再取得する（楽観的更新はしない）

作成・編集・削除の後は該当クエリを無効化して再取得する。楽観的更新はロールバック処理が必要になり、テンプレートとしては読む量が増える。案件で必要になったら足す。

### D3: 削除の確認は Phase 4 のモーダル部品を使う

`window.confirm` は使わない。ブラウザのモーダルダイアログは Playwright の実行を止める要因になり、スタイルも制御できない。Phase 4 で内製したモーダルを使う。

### D4: E2E は 1 本のスモークとし、複数の観点をその 1 本で通す

指示書の「Playwright はスモーク 1 本のみ」を優先する。貫通の流れ（ログイン → 一覧 → 作成 → 詳細 → 編集 → 削除）に、検索条件のリロード保持の確認を組み込む。

- これは e2e-conventions の「1 テスト = 1 検証意図」と緊張関係にある。本フェーズではスモークの検証意図を「参照実装が端から端まで壊れていないこと」と定義して 1 本に収める
- テストには複数の `@TP-NNN` タグを付け、どの観点を通しているかを追跡可能にする
- この判断は報告事項とし、テスト本数の方針を変える場合は test-plan から見直す

### D5: E2E 実行時のプロセス起動は Playwright の webServer に任せる

API・BFF・SPA と DB を、`make` のターゲット 1 つで起動できるようにし、`playwright.config.ts` の `webServer` からそれを呼ぶ。ローカルと CI で同じ起動経路にする（CI とローカルの手順一致という Phase 0 の原則）。

### D6: シードデータは fixture で投入し、テスト間で独立させる

ページネーションと検索条件の確認に必要な件数のデータを fixture で投入する。テストの実行順に依存しない状態にし、fixture 名と作られる状態の対応を `tests/e2e/fixtures/README.md` に記録する。

- ログイン操作はテスト本体に書かず fixture で行う（e2e-conventions）

## Risks / Trade-offs

- **スモーク 1 本に観点を詰め込むと、失敗時の切り分けが難しくなる** → Playwright の `test.step` で区切り、trace を有効にする。それでも切り分けが辛いなら本数の方針を見直す（D4 の報告事項）
- **E2E が CI を不安定にする（フレーク）** → `playwright.config.ts` の `retries: 1` によりリトライ成功はフレークとして記録される。フレークが続く場合はアサーションを緩めず原因を潰す（e2e-conventions の禁止事項）
- **3 プロセス + DB の起動が CI で遅い / 不安定** → 起動経路を `make` に一本化し、ローカルで同じ失敗を再現できるようにする
- **アクセシブルネーム依存のロケーターが UI 文言変更で壊れる** → 文言変更は仕様変更として test-plan に反映してから行う（e2e-conventions）。この運用を `apps/web/AGENTS.md` に明記する
- **楽観的更新を入れないことによる体感速度** → 参照実装としては素直さを優先する。案件側で足せる
