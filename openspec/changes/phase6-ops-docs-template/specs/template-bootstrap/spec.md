## Purpose

このリポジトリをテンプレートとして新規案件を立ち上げる利用者に対し、何を書き換えるべきか・運用で何をどう扱うか・どの判断がなぜ下されたかを提供する。テンプレートの価値は動作より引き継ぎ可能性で決まるため、その部分を明示的な成果物として定める。

## ADDED Requirements

### Requirement: 新規案件立ち上げのチェックリスト

リポジトリは、テンプレートから複製した直後に書き換えるべき箇所のチェックリストを提供しなければならない (MUST)。チェックリストは、モジュールパス、パッケージ名、サンプルリソース名、CI のシークレット名、およびテンプレート専用に無効化されている検証の解除を含まなければならない (MUST)。チェックリストをすべて適用したあと、テンプレート由来の識別子がリポジトリに残ってはならない (MUST NOT)。

#### Scenario: チェックリストの適用で識別子が残らない

- **WHEN** テンプレートを複製し、チェックリストの項目をすべて適用したあと、テンプレート固有の識別子を全文検索する
- **THEN** ドキュメント上の言及を除き、テンプレート由来の識別子が残っていない

#### Scenario: チェックリスト適用後もビルドと検証が通る

- **WHEN** チェックリストの項目をすべて適用した状態で、リポジトリの標準的な検証コマンドを実行する
- **THEN** 検証が成功する

#### Scenario: 書き換え対象の網羅

- **WHEN** チェックリストの項目を確認する
- **THEN** モジュールパス、パッケージ名、サンプルリソース名、CI のシークレット名、テンプレート専用に無効化されている検証の解除がいずれも含まれている

#### Scenario: テンプレート専用に無効化された検証が有効になる

- **WHEN** チェックリストの項目をすべて適用した複製先で、E2E 観点を持つ change を test-plan.md 付きで追加し、対応するタグ付きテストを用意しないまま検証を実行する
- **THEN** 検証が失敗する（テンプレート側で無効化されていた検証が、複製先では有効になっている）

#### Scenario: 解除漏れの検出

- **WHEN** テンプレート専用の無効化設定を解除しないまま、チェックリストの検証手順を実行する
- **THEN** 解除されていないことが検出される

### Requirement: 採用技術と選定理由の記録

リポジトリは、採用した主要ライブラリのバージョンと選定理由を記録しなければならない (MUST)。各ライブラリについて、次のメジャー移行で問題になり得る点を記載しなければならない (MUST)。

#### Scenario: 採用バージョンの追跡

- **WHEN** 依存宣言に含まれる主要ライブラリについて記録を参照する
- **THEN** 採用バージョン、選定理由、次のメジャーで壊れそうな点が記載されている

### Requirement: 運用手順の提供

リポジトリは、運用時に必要となる手順を参照可能な形で提供しなければならない (MUST)。少なくとも、データベースのマイナー / メジャーアップグレード手順、インフラ provider のメジャー更新手順、依存更新 Pull Request のレビュー基準、脆弱性警告の切り分け方針、障害時の初動を含まなければならない (MUST)。依存更新のレビュー基準と脆弱性警告の切り分けは、本番配信物に含まれるか否かで扱いを分けなければならない (MUST)。

#### Scenario: 障害時の追跡手順

- **WHEN** 障害が発生した状況を想定し、運用手順に従ってログからリクエストを追跡する
- **THEN** リクエスト ID を用いて対象リクエストのログを特定する手順が示されている

#### Scenario: 依存更新の扱い分け

- **WHEN** 本番配信物に含まれない依存の脆弱性警告について、対応の優先度を運用手順で確認する
- **THEN** 本番配信物に含まれる依存とは異なる優先度が示されている

### Requirement: メジャーアップグレード手順の提供

リポジトリは、主要な依存についてメジャー更新の手順を提供しなければならない (MUST)。手順は、実施時に判明した問題を書き足していく場所として位置づけられていなければならない (MUST)。

#### Scenario: 主要依存の更新手順

- **WHEN** フロントエンドおよびバックエンドの主要な依存について更新手順を参照する
- **THEN** それぞれの手順が記載されており、追記する場所であることが明示されている

### Requirement: 設計判断の記録

Phase を通じて下された主要な設計判断は、判断・理由・検討した代替案を含む記録として残さなければならない (MUST)。

#### Scenario: 判断の追跡

- **WHEN** 主要な設計判断について、なぜその選択をしたかを調べる
- **THEN** 判断内容・理由・検討した代替案が記録から読み取れる

### Requirement: Coding Agent 向け指示の階層分離

リポジトリは Coding Agent 向けの指示を階層ごとに分離しなければならない (MUST)。ルートの指示は、共通ルールと、どの階層の指示を読むべきかの案内に限定しなければならない (MUST)。フロントエンドの作業時にバックエンドの文脈を読む必要があってはならない (MUST NOT)。

#### Scenario: 階層ごとの指示

- **WHEN** フロントエンドの作業を想定してルートの指示を読む
- **THEN** フロントエンドの階層の指示に案内され、バックエンド固有の文脈は含まれていない

### Requirement: 静的配信の要件明示

リポジトリは、フロントエンドを静的配信する際のキャッシュ設定要件を明示しなければならない (MUST)。要件は、エントリ HTML をキャッシュさせないこと、内容ハッシュ付きアセットを長期キャッシュ可能として扱うこと、存在しないパスへのアクセスをエントリ HTML に 200 で解決することを含まなければならない (MUST)。

#### Scenario: 配信要件の参照

- **WHEN** フロントエンドの配信設定を行う立場で要件を参照する
- **THEN** エントリ HTML のキャッシュ抑止、ハッシュ付きアセットの長期キャッシュ、存在しないパスのフォールバックの 3 点が記載されている

#### Scenario: 実行時設定ファイルの扱い

- **WHEN** 実行時設定ファイルのキャッシュ設定について要件を参照する
- **THEN** キャッシュさせない設定が必要である旨が記載されている
