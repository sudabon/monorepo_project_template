## ADDED Requirements

### Requirement: 契約の値制約と実装側検証の一致

契約が定める入力の値制約（文字列長、禁止文字など）は、サーバ実装の検証とクライアント実装の検証の双方で、同じ境界値によって受理・拒否されなければならない (MUST)。契約と実装のいずれかだけが変更され制約がずれた場合、CI がそれを検出しなければならない (MUST)。制約の実装を 1 か所に統合することは要求しない。検証の重複を許したうえで、ズレを検出できることを要求する。

#### Scenario: 契約だけを変更するとずれが検出される

- **WHEN** 契約の値制約だけを変更し、サーバとクライアントの検証を更新しないまま検証を実行する
- **THEN** 検証が失敗し、一致していない制約が出力される

#### Scenario: 境界値の扱いが両実装で一致する

- **WHEN** 契約が定める上限ちょうどの長さの入力と、上限を 1 文字超えた入力を、サーバ実装とクライアント実装の双方に与える
- **THEN** 双方が同じ入力を受理し、同じ入力を拒否する

#### Scenario: 禁止文字の扱いが両実装で一致する

- **WHEN** 契約が禁止する文字を含む入力を、サーバ実装とクライアント実装の双方に与える
- **THEN** 双方が拒否し、契約が定めるエラー形式で違反フィールドを特定できる

## MODIFIED Requirements

### Requirement: 生成物とアプリケーション層の分離

TypeScript クライアントは、生成物の上に手書きの薄いラッパ層を持たなければならない (MUST)。生成物そのものを編集してはならない (MUST NOT)。ラッパはサーバ状態管理ライブラリの取得系クエリ定義と更新系 mutation 定義を返す形で、アプリケーションから利用できなければならない (MUST)。ラッパはキャッシュ無効化に使う識別子も公開しなければならない (MUST)。アプリケーションがその識別子を文字列リテラルで組み立ててはならない (MUST NOT)。

#### Scenario: ラッパ経由でのクエリ定義取得

- **WHEN** アプリケーションが `packages/api-client` の手書きラッパから、サンプルリソースの一覧取得に対応するクエリ定義を取得する
- **THEN** 契約から生成された型でパラメータとレスポンスが型付けされたクエリ定義が返る

#### Scenario: 生成物は手編集されていない

- **WHEN** 生成物ファイルに対してコード生成を再実行する
- **THEN** 差分が発生せず、手編集が混入していないことが確認できる

#### Scenario: ラッパ経由での更新定義取得

- **WHEN** アプリケーションが手書きラッパから作成・更新・削除に対応する定義を取得する
- **THEN** 契約から生成された型で入力とレスポンスが型付けされた `mutationOptions` が返り、操作は mutation 実行時に行われる

#### Scenario: キャッシュ無効化の識別子をラッパから得る

- **WHEN** アプリケーションが作成・更新・削除の後にサンプルリソースのキャッシュを無効化する
- **THEN** 無効化に使う識別子をラッパから取得しており、識別子の形を変更するとアプリケーション側が型検査で検出される
