# api-contract Specification

## Purpose
Go サーバと TypeScript クライアントの間の API 契約を単一のファイルに集約し、そこから両言語のコードを生成することで、型の二重管理と実装間の齟齬を構造的に排除する。

## Requirements

### Requirement: 契約の単一ソース

`api/openapi.yaml` は Go と TypeScript の間の唯一の契約でなければならない (MUST)。Go の実装コードから OpenAPI 仕様を生成してはならない (MUST NOT)。両言語の型定義および通信コードは、この仕様ファイルから生成しなければならない (MUST)。

#### Scenario: 仕様変更が両言語に反映される

- **WHEN** `api/openapi.yaml` のスキーマにフィールドを 1 つ追加してコード生成を実行する
- **THEN** Go の生成物と TypeScript の生成物の両方に、そのフィールドが反映される

#### Scenario: 契約は実装から独立している

- **WHEN** Go の実装コードだけを変更してコード生成を実行する
- **THEN** `api/openapi.yaml` は変更されない

### Requirement: サンプルリソースの操作定義

契約は、参照実装となるリソース 1 つに対する一覧取得・単体取得・作成・更新・削除の操作を定義しなければならない (MUST)。一覧取得はページネーションを持たなければならない (MUST)。

#### Scenario: CRUD 操作の網羅

- **WHEN** 契約に定義された操作を列挙する
- **THEN** サンプルリソースに対する一覧取得・単体取得・作成・更新・削除のすべてが定義されている

#### Scenario: 一覧取得のページネーション

- **WHEN** 一覧取得の操作定義を確認する
- **THEN** ページ位置を指定するパラメータと、総件数または次ページの有無を返すレスポンススキーマが定義されている

### Requirement: エラーレスポンスの統一形式

契約は、すべての操作で共通に使えるエラーレスポンススキーマを定義しなければならない (MUST)。バリデーションエラーは、どのフィールドがなぜ不正なのかをクライアントが機械的に判別できる形式でなければならない (MUST)。

#### Scenario: 共通エラースキーマ

- **WHEN** 任意の操作のエラーレスポンス定義を確認する
- **THEN** 共通のエラースキーマを参照しており、操作ごとに独自のエラー形状を定義していない

#### Scenario: バリデーションエラーのフィールド特定

- **WHEN** バリデーションエラーのレスポンススキーマを確認する
- **THEN** 対象フィールドの識別子とエラー内容の組を、複数件返せる構造で定義している

### Requirement: 生成の冪等性

コード生成は冪等でなければならない (MUST)。生成物を編集していない状態で生成を再実行しても、差分が発生してはならない (MUST NOT)。

#### Scenario: 生成の再実行で差分が出ない

- **WHEN** 生成物を編集していない状態でコード生成を 2 回連続で実行する
- **THEN** 2 回目の実行後に作業ツリーの差分が存在しない

### Requirement: 仕様と生成物の不一致検出

生成物はリポジトリにコミットしなければならない (MUST)。CI は、仕様を変更して生成物を更新していない Pull Request を失敗させなければならない (MUST)。

#### Scenario: 生成し忘れた PR が落ちる

- **WHEN** `api/openapi.yaml` だけを変更し、生成物を更新していない Pull Request を作成する
- **THEN** CI の契約検証が失敗する

#### Scenario: 仕様と生成物が揃った PR は通る

- **WHEN** `api/openapi.yaml` の変更と、それに対応する生成物の更新を含む Pull Request を作成する
- **THEN** CI の契約検証が成功する

### Requirement: 契約ファイルの lint

CI は `api/openapi.yaml` を静的検査し、規約違反を検出しなければならない (MUST)。

#### Scenario: 規約違反の仕様が検出される

- **WHEN** 規約に違反した記述を含む `api/openapi.yaml` で CI を実行する
- **THEN** 契約検証ワークフローの lint ステップが失敗し、違反箇所が出力される

### Requirement: 生成物とアプリケーション層の分離

TypeScript クライアントは、生成物の上に手書きの薄いラッパ層を持たなければならない (MUST)。生成物そのものを編集してはならない (MUST NOT)。ラッパはサーバ状態管理ライブラリの取得系クエリ定義と更新系 mutation 定義を返す形で、アプリケーションから利用できなければならない (MUST)。

#### Scenario: ラッパ経由でのクエリ定義取得

- **WHEN** アプリケーションが `packages/api-client` の手書きラッパから、サンプルリソースの一覧取得に対応するクエリ定義を取得する
- **THEN** 契約から生成された型でパラメータとレスポンスが型付けされたクエリ定義が返る

#### Scenario: 生成物は手編集されていない

- **WHEN** 生成物ファイルに対してコード生成を再実行する
- **THEN** 差分が発生せず、手編集が混入していないことが確認できる

#### Scenario: ラッパ経由での更新定義取得

- **WHEN** アプリケーションが手書きラッパから作成・更新・削除に対応する定義を取得する
- **THEN** 契約から生成された型で入力とレスポンスが型付けされた `mutationOptions` が返り、操作は mutation 実行時に行われる

### Requirement: サンプルリソースの NUL 文字禁止

OpenAPI 契約は Item と ItemInput の name / description に NUL（U+0000）を含められないことを pattern と説明で明記しなければならない (MUST)。作成・更新で NUL を含む入力は、既存の ValidationError 形式と HTTP 422 で拒否することを明記しなければならない (MUST)。

#### Scenario: 入出力の文字列制約

- **WHEN** Item または ItemInput の name / description を契約に従って検証する
- **THEN** NUL を含む文字列は不正となり、文字数制約を満たす通常の改行や文字列としての `\u0000` は許可される

#### Scenario: NUL 入力へのエラー形式

- **WHEN** NUL を含む作成・更新リクエストへの契約上の応答を確認する
- **THEN** HTTP 422 と ValidationError の code / message / errors により、違反フィールドと理由を取得できる
