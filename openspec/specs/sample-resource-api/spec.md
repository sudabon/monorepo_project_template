# sample-resource-api Specification

## Purpose
契約に定義されたサンプルリソースを、永続化を伴う実際の HTTP API として提供する。以降の案件がコピーして肉付けするための参照実装であり、CRUD・ページネーション・エラー応答の型を定める。

## Requirements

### Requirement: サンプルリソースの CRUD

サービスは、契約に定義されたサンプルリソースに対する一覧取得・単体取得・作成・更新・削除を HTTP で提供しなければならない (MUST)。作成および更新した内容は永続化され、後続の取得で読み出せなければならない (MUST)。

#### Scenario: 作成した内容が取得できる

- **WHEN** サンプルリソースを作成し、返却された識別子で単体取得する
- **THEN** 作成時に指定した内容が返る

#### Scenario: 更新した内容が反映される

- **WHEN** 既存のサンプルリソースを更新し、同じ識別子で単体取得する
- **THEN** 更新後の内容が返る

#### Scenario: 削除したリソースは取得できない

- **WHEN** 既存のサンプルリソースを削除し、同じ識別子で単体取得する
- **THEN** リソースが存在しないことを示す応答が返る

#### Scenario: プロセス再起動をまたいだ永続化

- **WHEN** サンプルリソースを作成したあとサービスを再起動し、同じ識別子で単体取得する
- **THEN** 作成した内容が返る

### Requirement: 一覧取得のページネーション

一覧取得は、契約に定義されたページネーションに従わなければならない (MUST)。ページ位置の指定に応じて返す件数と対象を変え、総件数または次ページの有無をクライアントが判別できる形で返さなければならない (MUST)。

#### Scenario: ページ位置に応じた分割

- **WHEN** 1 ページに収まらない件数のリソースが存在する状態で、1 ページ目と 2 ページ目を取得する
- **THEN** それぞれ異なるリソース集合が返り、重複と欠落がない

#### Scenario: 空の一覧

- **WHEN** リソースが 1 件も存在しない状態で一覧取得する
- **THEN** エラーではなく空の一覧が返り、総件数(または次ページ有無)が空であることを示す

### Requirement: 入力検証と検証エラー応答

サービスは、契約に定義された制約に違反する入力を拒否しなければならない (MUST)。拒否する場合、契約に定義されたバリデーションエラー形式で、違反したフィールドとその理由を返さなければならない (MUST)。

#### Scenario: 単一フィールドの検証エラー

- **WHEN** 契約の制約に違反する値を 1 つ含むリクエストで作成を試みる
- **THEN** 検証エラーとして拒否され、応答に該当フィールドの識別子と理由が含まれる

#### Scenario: 複数フィールドの検証エラー

- **WHEN** 契約の制約に違反する値を複数含むリクエストで作成を試みる
- **THEN** 違反したすべてのフィールドが 1 回の応答にまとめて含まれる

#### Scenario: 検証エラー時に永続化されない

- **WHEN** 検証エラーとなるリクエストで作成を試みたあと、一覧を取得する
- **THEN** 当該リソースは作成されていない

#### Scenario: NUL 文字を含む作成・更新の拒否

- **WHEN** name または description に NUL（U+0000）を含む作成・更新リクエストを送信する
- **THEN** 422 の `validation_error` 応答に違反したすべてのフィールドと理由が含まれ、リソースは作成されず、既存リソースも変更されない

#### Scenario: NUL ではないエスケープ文字列と改行

- **WHEN** NUL を含まず、文字列としての `\u0000` や改行を含む有効な入力を送信する
- **THEN** 文字列の内容を変えずに保存・取得できる

### Requirement: 存在しないリソースの扱い

存在しない識別子に対する単体取得・更新・削除は、リソースが存在しないことを示す応答を返さなければならない (MUST)。内部エラーとして扱ってはならない (MUST NOT)。

#### Scenario: 存在しない識別子での操作

- **WHEN** 存在しない識別子で単体取得・更新・削除をそれぞれ実行する
- **THEN** いずれもリソース不在を示す応答が返り、サーバ内部エラーにはならない

### Requirement: 層構造と依存の向き

実装は handler / usecase / domain / repository の層に分割しなければならない (MUST)。依存の向きは内側（domain）を向いていなければならず、domain から外側の層への依存があってはならない (MUST NOT)。この制約は機械的に検査できなければならない (MUST)。

#### Scenario: 逆方向の依存が検出される

- **WHEN** domain 層から handler 層または repository 実装への依存を追加して検査を実行する
- **THEN** 検査が失敗し、違反箇所が出力される

#### Scenario: 契約の実装漏れが検出される

- **WHEN** 契約に定義された操作のうち 1 つを実装しない状態でビルドする
- **THEN** ビルドが失敗する
