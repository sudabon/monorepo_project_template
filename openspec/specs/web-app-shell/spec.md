# web-app-shell Specification

## Purpose
SPA の骨格として、環境非依存のビルド成果物・認証ガード・サーバ状態の既定方針・障害時の表示・フォーム検証の型を提供する。以降の画面はこの上に載るため、ここで決めた振る舞いが全画面の初期値になる。

## Requirements

### Requirement: 実行時設定の読み込み

ビルド成果物は環境に依存してはならない (MUST NOT)。アプリケーションは起動時に設定ファイルを取得し、API の接続先などをそこから読まなければならない (MUST)。設定の取得に失敗した場合、アプリケーションは無反応にならず、設定を読めなかったことが利用者に分かる状態で表示されなければならない (MUST)。

#### Scenario: 設定ファイルの差し替えで接続先が変わる

- **WHEN** 同一のビルド成果物を配信し、設定ファイルの API 接続先だけを別の値に差し替えて起動する
- **THEN** アプリケーションは差し替え後の接続先に対して通信する

#### Scenario: 設定ファイルが取得できない

- **WHEN** 設定ファイルが取得できない状態でアプリケーションを起動する
- **THEN** 白画面にならず、設定を読み込めなかったことを示す表示が出る

#### Scenario: 設定ファイルの内容が不正

- **WHEN** 設定ファイルが期待する形式を満たさない状態でアプリケーションを起動する
- **THEN** 不正であることを検知し、エラー表示に至る（不正な値のまま通信を試みない）

### Requirement: 認証ガード付きルーティング

保護されたルートは、遷移が完了する前に認証状態を判定しなければならない (MUST)。未認証の場合、保護されたルートの内容を表示してはならず (MUST NOT)、ログイン画面へ遷移させなければならない (MUST)。

#### Scenario: 未認証で保護ルートへ遷移する

- **WHEN** 未認証の状態で保護されたルートの URL を直接開く
- **THEN** 保護ルートの内容が表示されることなくログイン画面が表示される

#### Scenario: 認証済みで保護ルートへ遷移する

- **WHEN** 認証済みの状態で保護されたルートへ遷移する
- **THEN** 保護ルートの内容が表示される

#### Scenario: ログイン画面の表示

- **WHEN** 未認証の状態でアプリケーションを開く
- **THEN** ログイン画面が表示される

### Requirement: サーバ状態の既定方針とグローバルエラー処理

サーバ状態の取得に関する既定値（再取得の鮮度・再試行・ウィンドウフォーカス時の再取得）は 1 か所で明示的に定義しなければならない (MUST)。エラーは種類に応じて扱いを分けなければならない (MUST): 認証エラーはセッション切れとして扱いログイン画面へ遷移させ、サーバ内部エラーは利用者に通知し、いずれにも該当しないエラーは握りつぶしてはならない (MUST NOT)。

#### Scenario: 認証エラーでログインへ戻る

- **WHEN** 保護された画面の表示中に、サーバが認証エラーを返す
- **THEN** セッション切れとして扱われ、ログイン画面へ遷移する

#### Scenario: サーバ内部エラーの通知

- **WHEN** 操作に対してサーバが内部エラーを返す
- **THEN** 利用者にエラーが通知され、画面が白画面にならない

#### Scenario: 未分類のエラーが表示される

- **WHEN** 認証エラーでもサーバ内部エラーでもない失敗が発生する
- **THEN** その失敗が利用者に見える形で表示され、無言で無視されない

### Requirement: エラー境界による障害時表示

アプリケーションはルート単位のエラー境界と、最上位のエラー境界を持たなければならない (MUST)。予期しない例外が発生しても、アプリケーション全体が空白の表示になってはならない (MUST NOT)。最上位のエラー境界には、監視サービスへ送信するための差し込み口を用意しなければならない (MUST)。

#### Scenario: ルート内の例外が局所化される

- **WHEN** ある画面の描画中に予期しない例外が発生する
- **THEN** その画面の範囲にエラー表示が出て、アプリケーション全体は操作可能なまま残る

#### Scenario: API 停止時に白画面にならない

- **WHEN** API に到達できない状態でアプリケーションを操作する
- **THEN** 白画面ではなくエラー表示が出る

#### Scenario: 監視送信の差し込み口

- **WHEN** 最上位のエラー境界が例外を捕捉する
- **THEN** 監視サービスへの送信フックが例外情報とともに呼び出される（既定では何も送信しない）

### Requirement: フォーム検証とサーバ検証エラーの反映

フォームは送信前にクライアント側で入力を検証しなければならない (MUST)。検証規則は、可能な範囲で API 契約の制約に対応していなければならない (MUST)。サーバから契約のバリデーションエラー形式で返された内容は、対応するフォーム項目のエラーとして表示しなければならない (MUST)。対応する項目が特定できないサーバ検証エラーも、利用者に見える形で表示しなければならない (MUST)。

#### Scenario: クライアント側の検証で送信が止まる

- **WHEN** 契約の制約に違反する入力でフォームを送信しようとする
- **THEN** 送信されず、該当項目にエラーが表示される

#### Scenario: サーバ検証エラーが項目に反映される

- **WHEN** クライアント側の検証を通過した入力に対し、サーバが特定フィールドのバリデーションエラーを返す
- **THEN** 該当するフォーム項目にそのエラーが表示される

#### Scenario: 項目に対応しないサーバ検証エラー

- **WHEN** サーバが、フォーム上の項目に対応付けられないバリデーションエラーを返す
- **THEN** そのエラーがフォーム全体のエラーとして表示され、無視されない

### Requirement: UI 部品の内製

汎用 UI 部品（ボタン、入力、モーダル、テーブル、トースト）はリポジトリ内のコードとして保持しなければならない (MUST)。UI コンポーネントライブラリを依存パッケージとして追加してはならない (MUST NOT)。

#### Scenario: UI ライブラリへの依存がない

- **WHEN** `apps/web` の依存宣言を確認する
- **THEN** UI コンポーネントライブラリが依存に含まれていない

#### Scenario: 汎用部品がリポジトリ内に存在する

- **WHEN** 汎用 UI 部品の実体を探す
- **THEN** ボタン・入力・モーダル・テーブル・トーストがリポジトリ内のソースとして存在し、編集可能である
